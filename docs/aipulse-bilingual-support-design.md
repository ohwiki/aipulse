# AIpulse 双语支持设计方案

更新时间：2026-05-09

## 目的

本文档用于约束 `AIpulse` 后续的中英文支持方案，避免后续模型或开发者直接把整站做成维护成本很高、SEO 边界混乱的“半成品国际化站点”。

本文档的核心目标不是立刻把 `AIpulse` 改造成完整英文站，而是先定义：

1. 双语支持到底支持到什么程度
2. 先做什么，后做什么
3. 工程层应该如何抽象，避免后面越改越乱

## 当前判断

`AIpulse` 现在**可以支持中文和英文**，但不建议一开始就做成完整双语站。

当前更合理的目标是：

- 先支持中英文界面文案切换
- 先支持内容卡片的中英展示策略
- 先支持页面元信息的双语能力
- 暂不立即进入 `/en/` 独立站点路由体系

## 为什么不建议一步到位做完整双语站

### 1. 当前产品主定位仍是中文从业者资讯站

现在站点核心定位仍然是：

- 面向中文 AI 从业者
- 提供中文整理后的资讯入口
- 用中文摘要降低阅读门槛

如果直接做成“完整双语站”，会立刻带来额外复杂度，但对当前阶段的搜索和产品收益不一定最大。

### 2. 当前内容结构天然偏“中文主站 + 英文源辅助”

当前内容层特点是：

- 原始来源很多是英文
- 站内核心整理价值是中文标题与中文摘要
- `titleEn` 已经存在，但英文摘要、英文说明页、英文 SEO 体系并未完整建立

因此更合理的路线不是“立刻全量翻到英文”，而是先建立双语能力层。

### 3. 完整双语站会明显抬高工程与 SEO 成本

如果直接做完整双语站，至少要同时处理：

- 路由
- locale 状态
- 页面字典
- SEO title/description 双语
- `hreflang`
- 双语 sitemap
- About / Privacy / Methodology / Sources 等说明页双语
- 内容字段回退逻辑

这会显著增加当前项目复杂度。

## 推荐路线

## 阶段 1：双语能力层

这是当前最推荐优先做的阶段。

目标：

- 支持中英文 UI 文案切换
- 支持内容字段双语显示策略
- 支持页面元信息双语生成
- 不强制引入独立英文路由

### 阶段 1 具体范围

#### 1. UI 文案字典化

把以下内容从页面内硬编码提出来：

- 顶部导航
- 页面标题区文案
- 按钮文案
- section 标题
- trust pages 文案
- footer 说明

建议建立类似结构：

```ts
export type Locale = "zh-CN" | "en";

export const messages = {
  "zh-CN": {
    nav: {
      today: "今日",
      archive: "归档",
      category: "分类",
      about: "关于"
    }
  },
  en: {
    nav: {
      today: "Today",
      archive: "Archive",
      category: "Topics",
      about: "About"
    }
  }
};
```

#### 2. 内容展示双语策略

内容条目应定义清楚中英文模式下怎么展示。

推荐规则：

### 中文模式

- 主标题：中文标题
- 副标题：英文原标题（弱显示，可选）
- 摘要：中文摘要

### 英文模式

- 主标题：英文原标题优先
- 如果英文原标题不存在，再回退中文标题
- 摘要：
  - 如果未来有英文摘要，用英文摘要
  - 如果没有英文摘要，允许：
    - 显示中文摘要
    - 或直接隐藏摘要

后续应明确哪一种策略更符合产品定位。

#### 3. 页面元信息双语能力

后续 `BaseLayout` 应支持按 locale 输出：

- `lang`
- `title`
- `description`
- `og:locale`
- JSON-LD 中的 `inLanguage`

注意：当前 `zh-CN` 是默认语言，后续切到英文时不能只改页面文字，不改 metadata。

#### 4. 信任页与说明页双语化

以下页面如果支持英文，不能只翻导航，不翻正文：

- About
- Privacy
- Contact
- Methodology
- Sources and Attribution

否则会出现“英文 UI + 中文正文”的割裂体验。

## 阶段 2：页面级双语模式

在阶段 1 完成后，再决定是否进入阶段 2。

阶段 2 的目标是：

- 页面本身根据 locale 完整切换
- 中文用户和英文用户都能得到完整一致的页面体验

此阶段才适合进一步讨论：

- 顶部语言切换控件
- URL 参数或客户端语言状态
- 默认语言策略

## 阶段 3：真正双语站

只有在明确需要英文 SEO 和英文用户入口时，才建议进入这个阶段。

### 阶段 3 特征

- `/` 中文主站
- `/en/` 英文站
- 每个页面都有独立英文路由
- 每页都有中英文 canonical / `hreflang`
- 需要双语 sitemap

### 只有在以下条件满足时才建议进入阶段 3

1. 已经确认有真实英文用户需求
2. 已经具备较稳定的英文文案与英文摘要来源
3. 愿意承担双语 SEO 维护成本

## 当前推荐方案

对 `AIpulse` 当前阶段，推荐方案如下：

### 推荐方案

**阶段 1 + 预留阶段 2，不直接进入阶段 3**

也就是说：

1. 先建立 locale、字典、内容回退和 metadata 能力
2. 先支持中英文界面和条目展示逻辑
3. 先不要直接上 `/en/` 路由

## 工程设计建议

### 1. 定义统一 locale 类型

```ts
export type Locale = "zh-CN" | "en";
```

### 2. 建立独立文案字典层

建议新增类似文件：

- `src/lib/i18n/messages.ts`
- `src/lib/i18n/types.ts`
- `src/lib/i18n/get-locale.ts`

### 3. 建立内容字段回退策略

建议定义清楚：

- `getDisplayTitle(item, locale)`
- `getDisplaySummary(item, locale)`
- `getLocaleMeta(locale, pageType, data)`

不要在组件里到处写三元表达式。

### 4. 让组件消费“已决定好的文案”

组件层应该尽量少知道语言逻辑，只接收：

- 已经选好的标题
- 已经选好的摘要
- 已经选好的按钮文字

否则后面每个组件都会变成 i18n 判断点。

### 5. 不要先做客户端花哨切换

当前阶段更适合：

- 构建期或服务端确定语言
- 或最简单的 query/cookie 级切换

不要一开始就引入复杂前端状态管理，只为了做一个语言按钮。

## 页面层双语支持优先级

### 第一优先级

1. Header / Footer
2. 首页
3. 分类页
4. 单日页

### 第二优先级

1. About
2. Privacy
3. Contact
4. Methodology
5. Sources and Attribution

### 第三优先级

1. 双语 SEO
2. 双语 structured data
3. 双语 sitemap / `hreflang`

## 内容层现实约束

后续任何模型都必须承认一个现实：

当前数据层并没有完整英文摘要体系。

因此在真正进入英文模式前，应先明确：

1. 英文模式是否接受没有英文摘要
2. 是否允许英文模式下显示中文摘要
3. 是否要在 pipeline 层补英文摘要生成

这不是纯前端问题，而是内容供应问题。

## 不要做的事

后续默认不要做以下事情，除非用户明确要求：

- 直接把所有页面复制一份做 `/en/`
- 先做语言按钮，再临时补文案
- 让页面同时混杂过多中英文而没有规则
- 让英文模式下出现大量中文固定文案
- 在组件内部到处散落 locale 判断

## 当前最合理的后续动作

如果后续准备正式做双语支持，推荐顺序是：

1. 先写 locale / i18n 基础设计
2. 先抽 Header / Footer / trust pages 文案
3. 再抽首页和卡片展示逻辑
4. 最后再决定要不要进入 `/en/` 路由级双语

## 总结

`AIpulse` 可以支持中文和英文，但当前阶段最正确的做法不是“立刻做完整双语站”，而是“先建立双语能力层，再逐步推进到页面级和路由级支持”。

后续任何大模型若参与该能力建设，应默认以此文档为准，不应直接跳到高成本的完整国际化方案。
